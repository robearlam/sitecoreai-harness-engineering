## Technical Approach

Add one new Sitecore-rendered **server component**, `CallToActionBanner`, in its own folder under `src/components/`. Register it through the existing `sitecore-tools` generate-map flow. The existing `headless-main` `AppPlaceholder` in `src/Layout.tsx` renders it. Routing, the Sitecore client, layout, and providers do not change.

**Component key.** The generator keys the component map on the file's base name, so the component file is `CallToActionBanner.tsx` and the rendering's Component Name in Sitecore must be exactly `CallToActionBanner`.

**Data shape.** The component receives `fields` (the datasource) and `page`, as `ImageGallery` does. It reads editing state from `page.mode.isEditing`, so it needs no client hooks and stays a server component. Field typing reuses SDK types: `Field<string>` for Heading, `RichTextField` (or `Field<string>`) for Body, `LinkField` for both actions, and `ImageField` for the image. **Background Colour is typed as an optional resolved-item reference** (`id`, `name`, and `fields.Value` as a `Field<string>`). This matches the shape the Layout Service delivered in the first attempt (`{"id": "...", "name": "Primary", "fields": {"Value": {"value": "primary"}}}`). Hero Banner's `Field<string>` Droplink typing is not copied. Every field is optional in the type, and every field is guarded.

**Background-mode lookup (single source of truth).** A small pure helper in its own camelCase file resolves the background mode in two steps, as the design asks:

1. If the Background Image field has a `src`, the mode is **image**. This applies regardless of the colour selection (AC 10).
2. Otherwise, the mode is the option whose `fields.Value.value` matches a known key: `neutral-light`, `primary`, or `neutral-dark`. A missing Droplink, a missing `Value`, or an unknown value falls back to **neutral-light** (AC 9).

The helper returns one presentation record per mode: the band background, text colour, primary and secondary button treatments for the light or dark context, the focus-ring colour, and whether a scrim is shown. Every element of the banner draws from this record. The helper keys off the option item's `Value` field, not its item name, so renaming or translating the display name does not break the mapping. The helper is unit-tested on its own (TDD).

**Structure** (as the design describes):

- **Background band.** A full-width `<section>`, labelled by its heading through `aria-labelledby` when a heading is present. `headless-main` in `Layout.tsx` is not width-constrained (`<main><div id="content">`), so the band is full width as an ordinary block element. Do **not** copy Hero Banner's `w-screen` / negative-margin technique, which risks horizontal overflow from scrollbar width (Design: "no horizontal overflow at any width"). In image mode, the image is absolutely positioned to cover the band, cropped and centred, and does not set the height. The 60% black scrim sits above it. Both are hidden from assistive technology, and the image is rendered with empty alt (decorative).
- **Content container.** Reuses the app's existing content-container pattern, confirmed in `PromoCardGrid` and `ImageGallery`: centred, `max-w-7xl` maximum width, horizontal padding of 16px / 24px / 32px at base / `sm` / `lg`. This is the width the design note asked Planning to confirm.
- **Content stack.** Centred text in this order: `<h2>` heading (rendered through the SDK `Text` primitive with an `h2` tag), body (SDK `RichText`, capped at about `max-w-2xl` and centred, with nested links underlined and inheriting the text colour), then the action group (SDK `Link` for primary, then secondary).
- **Buttons.** Banner-level, two roles by two contexts, as the task's binding decision sets. Both buttons share one shape, reusing the app's existing minimal button: **`rounded` (4px) corners, 24px horizontal and 12px vertical padding, medium weight**, as Hero Banner's CTA uses. This confirms the radius the design asked about. Minimum height 44px. The secondary button has a 2px outline. The focus ring uses `focus-visible`, is 2px wide with a 2px offset, and its colour comes from the lookup. Hover is a colour shift only. The buttons stack, filling the container width with a comfortable maximum, below `sm`. From `sm` up they sit in a centred row that wraps, sized to their content.
- **Unique heading id.** More than one banner can sit on a page, so the heading id used by `aria-labelledby` must be unique per instance. Derive it from the rendering's `uid` (passed to the component by the placeholder) or React's `useId`. Do not use a fixed constant like `ImageGallery`'s.

**Normal-mode output rules** (AC 4–6): the body is omitted when its Rich Text is empty or whitespace. Each action is omitted when its link has no `href`. The action group is omitted when both actions are empty. The heading is omitted when empty, and the section then has no `aria-labelledby`. If `fields` is absent, the component returns `null`. There is no mock or fallback content.

**Editing-mode output rules** (AC 12–13): every text and link field is always rendered through its SDK primitive, so Pages shows its standard empty-field placeholder in position. The action group always shows two slots. An extra, labelled "Background image" slot below the action group renders the SDK `Image` primitive for the Background Image field, whether it is empty or set. When the image is set, the band also shows the image and scrim. This slot is never output in normal mode. Background Colour is not edited inline. Its help text, a CMS prerequisite, tells authors that the image overrides it.

## Risks

- **Droplink delivery shape.** The type assumes the resolved-item shape seen in the first attempt. If the Layout Service delivers a different shape (for example, only an id string), the resolver falls back to neutral-light silently. QA must check the layout JSON (AC 21) and confirm that `fields.Value.value` arrives.
- **Option `Value` keys must match exactly.** A typo in the CMS (for example `Primary` instead of `primary`) silently falls back to the default. The CMS Prerequisites give exact values, and the CMS record should show them.
- **SDK empty-field behaviour in Pages.** This plan relies on the SDK `Text`, `RichText`, `Link`, and `Image` primitives rendering editable placeholders for empty fields in metadata editing mode. If `Link` or `Image` render nothing when empty, the editing branch needs an explicit wrapper. Unit tests mock the primitives, so this can only be confirmed in Pages.
- **Decorative image alt.** The SDK `Image` primitive emits the authored alt by default. The component must override it to empty, or hide the wrapper from assistive technology, so the image stays decorative in normal mode.
- **Unique heading ids.** Several banners on one page would produce duplicate ids if a constant were used. Covered by a test.
- **Component name mismatch.** If the rendering's Component Name is not exactly `CallToActionBanner`, the placeholder shows a missing-component message. This is a CMS-side check.
- **First D-005 CMS run.** It is uncertain whether `create_component` creates the datasource folder, and whether `update_component` sets the Datasource Template. The CMS agent escalates if not (task risk). This does not block Build.
