## Carry-forward Resolutions

### 1. Page `h1` ownership — confirmed, with a recorded page-level gap

- `src/Layout.tsx` renders the `headless-header`, `headless-main`, and `headless-footer` placeholders inside `header`, `main`, and `footer` landmarks. It renders no heading of its own.
- The Hero Banner (`src/components/HeroBanner/HeroBanner.tsx`) renders its Heading as an `h1`. Its test asserts the `h1` level.
- No other `headless-main` component renders an `h1`. Promo Card Grid renders card titles as `h3`. Only the not-found and global-error fallbacks render an `h1`, and they are outside the Sitecore layout.
- **Conclusion:** the page `h1` is owned by the Hero Banner, so the gallery's fixed `h2` is correct (AC4). No heading-level field is added.
- **Page-level gap (recorded, not in scope):** a page authored without a Hero Banner has no `h1`. This is a page-composition gap and does not change the gallery. QA should note it if a test page lacks a Hero Banner, and it should not be raised as a gallery defect.

### 2. Multilist resolution and editing metadata (AC28, AC24) — confirmed mechanism, one runtime verification step

- **Mechanism used by Promo Card Grid (T005):** the component reads its Multilist (`fields.Cards`) straight from the rendering's `fields` prop as an ordered array of referenced items, each with `id` and `fields`. It uses no rendering-level query, no `getComponentServerProps`-style data fetch, and no second client. The resolved items are part of the default layout data that `AppPlaceholder` passes to the component.
- **SDK contract:** the Content SDK's component prop type models `fields` as `Field | Item | Item[]`. The `Item` type carries its own `fields` map of `Field` values. **The gallery adopts the same mechanism:**
  - `fields.Images` is an ordered array of Gallery Image items.
  - Each item's `fields.Image` is an image field and `fields.Caption` is a text field.
- **Editing metadata:** in the SDK types, every `Field` extends `FieldMetadata`, which has an optional `metadata` property populated in editing mode. Referenced items' fields therefore have the same shape as top-level fields. The SDK field components (`Text`, `NextImage`) render inline-editing chrome from that metadata.
- **Caveat:** Promo Card Grid does not prove that inline editing of referenced fields works. It renders `Title` and `Description` as raw `.value` strings rather than through the `Text` component. The gallery must therefore render the heading, captions, and images through the SDK field components in editing mode. It must not use raw values.
- **Page mode:** `AppPlaceholder` passes `page` (including `page.mode.isEditing`) to server components. `page` is a non-serialisable prop, so it is stripped for client components. The gallery's root rendering must therefore be a **server component** that reads `page.mode.isEditing` (AC27). This matches the check that `Layout.tsx` already uses.
- **Remaining runtime check:** confirming that XM Cloud Pages actually emits field metadata for Multilist-referenced items needs a live instance. It is a manual verification in QA and CMS Configuration, not a planning unknown. It cannot be confirmed from source, but the SDK contract supports it and no alternative mechanism is needed. If the metadata turns out to be missing at runtime, QA records it against AC24 and the human decides. Build must not introduce a separate data query to work around it.

## Technical Approach

The gallery is a standard Content SDK rendering under `src/components/ImageGallery/`. The `sitecore-tools` component map picks it up automatically and `AppPlaceholder` renders it in `headless-main`. Routing, layout, the placeholder flow, and the Sitecore client are all unchanged.

The client boundary follows the design note's three roles. It keeps the client surface small and works within the SDK constraint that only server components receive `page`.

1. **Gallery shell (server component, the registered rendering `ImageGallery`):**
   - Receives `fields` and `page` from the placeholder.
   - Owns the section wrapper and content container, matching neighbouring sections such as Promo Card Grid, and the `h2` heading.
   - Owns the decision between normal and editing mode, based on `page.mode.isEditing`.
   - Guards optional data explicitly. In normal mode, zero images renders nothing (AC16) and an empty heading renders no heading element (AC4).
   - In editing mode it renders the static editing list itself, with no client code (AC24–AC26).
   - In normal mode it passes the resolved, serialisable field data (items, heading text, and an id for labelling) to the interactive carousel.
2. **Interactive carousel (client component):**
   - Owns the current index, previous/next controls, indicators, the "x of y" counter, arrow-key handling, the polite live-region announcer, and the slide frame triggers.
   - Hides non-current slides from view, the accessibility tree, and the tab order (AC14).
   - Uses wrap-around index logic (AC10).
   - Hides the control row when there is only one image (AC15).
   - Owns whether the lightbox is open and which index it opened at, and renders the lightbox.
   - On close, takes the lightbox's last-viewed index and moves focus to that slide's trigger (AC22).
3. **Lightbox dialog (client component):**
   - Renders through a React portal to the document body, so it sits above page stacking contexts. This uses React only and adds no dependency.
   - Exposes `role="dialog"`, `aria-modal`, and the accessible name chain (AC18).
   - Moves focus to Close on open and contains Tab and Shift+Tab within the dialog (AC19).
   - Handles Left/Right, Escape, and backdrop clicks. Clicks on the image, caption, or controls do not close it (AC20, AC21).
   - Owns its own index, which starts from the carousel's index.
   - Locks body scroll while open, restores the scroll position and scrollability on close, and releases the lock on unmount (AC23).

**Pure logic** (wrap-around index arithmetic and the grouped hard-coded English label builders such as "Slide x of y", "Image x of y", "Go to slide n", and the trigger name with its empty-alt fallback) lives in a small non-component module with unit tests. The labels are grouped in one place so B012 can later swap them for dictionary values.

**Dialog implementation choice:** use a hand-rolled `role="dialog"` overlay with explicit focus containment rather than the native `<dialog>.showModal()`. The design note allows either, provided AC18–AC23 are met. The hand-rolled version has the same behaviour in every browser and can be tested reliably in Jest/jsdom, which does not implement `showModal` modal behaviour. No modal primitive exists in the app today, so nothing is being duplicated.

**Images (AC6):** use the SDK's `NextImage` field component, which runs through the Next.js image optimisation path, for both the carousel and the lightbox. Do not use the plain `Image` that Hero Banner and Promo Card Grid use, because it does not go through Next.js optimisation.

- **Carousel images:** fill the fixed-ratio frame with contain fit and a `sizes` hint matched to the content container width. Only the first slide is a priority load. Other slides load lazily, so hidden slides are not fetched at full size up front.
- **Lightbox image:** requested with a viewport-based `sizes` hint, so the optimiser serves a full-size rendition rather than the slide-size one.
- **Hosts:** the existing `images.remotePatterns` in `next.config.ts` already allow the XM Cloud edge and `xmc-*` media hosts, so no config change is expected.

**Styling:** Tailwind utilities with design-system tokens (AC8), following the design note for ratios (4:3 on mobile, 16:9 from tablet up), contain fit, the dark neutral scrim, minimal icon buttons with 44×44 targets, indicator dots with 24×24 targets and a pill-shaped current indicator, focus rings including a variant that is visible on the dark scrim, a caption area that reserves the height of the tallest caption, and reduced-motion handling. No custom CSS file is planned. Chevron and close glyphs are inline SVG. No icon library is used (AC30).

## Risks

- **Referenced-item editing metadata at runtime:** the SDK types support metadata on Multilist-referenced fields, but no existing component proves inline editing of referenced fields (Promo Card Grid renders raw values). If XM Cloud does not emit metadata for them, AC24 fails in Pages even though the code is correct. Mitigation: use the SDK field components throughout the editing path, and verify manually in QA. Do not add a workaround query.
- **`NextImage` and the editing / test environment:** `NextImage` relies on `next/image` and the configured remote patterns. Tests must mock it like the existing tests mock `Image`. If the media host in a given environment is not covered by `remotePatterns`, the images fail to optimise. The existing patterns cover XM Cloud edge and `xmc-*` hosts. Changing them is out of scope unless QA finds a gap.
- **Server-to-client prop serialisation:** only serialisable data (field objects, strings, ids) may cross into the client carousel. `page` and functions must not. The SDK field components used in the client must be client-safe.
- **jsdom limitations:** focus containment, the portal, and scroll lock must be testable in jsdom. Choosing a hand-rolled dialog over `showModal` mitigates this. Pixel layout (aspect ratio, no layout shift) cannot be unit-tested and is checked manually in QA.
- **Accessibility edge cases:** carousel and modal patterns are common WCAG failure points. Examples are live-region noise, focus loss when the slide trigger changes on close, and the focus ring's contrast on the scrim. The tests cover behaviour, and manual screen-reader checks remain necessary.
- **Component-map noise:** helper files appear as inert map entries, and client helpers also appear in the client map. This is consistent with the existing project pattern, but it is a known side effect of the generator.
- **Page-level `h1` gap:** pages without a Hero Banner have no `h1`. This is outside the gallery's scope and is recorded only.
