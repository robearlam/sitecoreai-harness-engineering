## Title

Call to Action Banner

---

## Feature Goal

Provide a reusable, full-width banner that invites visitors to take an action. It shows an authored heading, optional short body text, a primary action, and an optional secondary action, on an author-selected design-system background colour or an optional background image. The banner is placed in the `headless-main` placeholder and its content comes from a datasource item in the site's `Data` folder.

---

## User Value

- Visitors get a clear, prominent prompt to act (for example "Get in touch" or "Start your trial").
- Authors can place the same banner on several pages by sharing one datasource item, choose its look from a fixed, accessible set of backgrounds, and edit every field in Pages.

---

## In Scope

All content is driven by Sitecore-authored datasource data and rendered through the existing route, layout, placeholder, and component-map pipeline. Colour and layout styling is application-owned.

- A Call to Action Banner rendering registered in the existing component map and placed in `headless-main`.
- Datasource fields:
  - Heading (Single-Line Text)
  - Body (Rich Text, short-form, optional)
  - Primary Action (General Link)
  - Secondary Action (General Link, optional)
  - Background Colour (Droplink to background-colour option items, optional, with a default)
  - Background Image (Image, optional)
- Background colour options, binding human decision from the task file (Tailwind default palette, never `primary` utilities):

  | Option | Background | Text |
  |---|---|---|
  | Neutral Light (default) | `neutral-100` | `neutral-900` |
  | Primary | `blue-700` | `white` |
  | Neutral Dark | `neutral-900` | `white` |
  | Background image | black scrim | `white` |

- Button styling, banner-level decision:
  - On Primary, Neutral Dark, and image backgrounds: primary = white fill with `neutral-900` label; secondary = white outline with white label.
  - On Neutral Light: primary = `neutral-900` fill with white label; secondary = `neutral-900` outline with `neutral-900` label.
- Full-viewport-width banner with content constrained to the design-system content width; buttons stack on small viewports.
- Editing support in Pages for every field, including empty optional fields.
- Accessibility: semantic heading, buttons rendered as real links with discernible text, visible focus states, WCAG AA contrast.
- Sitecore items (through the CMS Configuration stage): datasource template, background-colour option template, options folder, one option item per allowed colour, rendering available on the `harness-engineering` site and allowed in `headless-main`, datasource folder under the site's `Data` folder, sample content on a page, and serialization coverage.
- Author help text on the Background Colour field stating that the image overrides the colour.
- Unit/component tests for the cases listed in the acceptance criteria.

---

## Out of Scope

- More than two action buttons, or buttons with icons.
- Free-form colour selection (hex values, colour pickers) or per-banner custom colours outside the fixed set.
- Video, animated, or parallax backgrounds.
- Layout variants (split image/text, alignment options, narrow or card styles).
- Rendering parameters or style variants; all configuration is in datasource fields.
- Click tracking, analytics events, personalisation, A/B testing.
- Dictionary-driven labels (B012) and localisation beyond existing Sitecore item languages.
- Changes to, or code sharing with, the Hero Banner beyond existing design-system utilities.
- Mock or fallback content when the CMS returns no data.

## Acceptance Criteria

Numbered for QA traceability.

**Rendering and composition**

1. With a datasource set, the banner renders in the `headless-main` placeholder through the existing layout and component-map pipeline, showing the authored heading and the primary action link (label and href from the General Link field).
2. The banner background spans the full viewport width; its content is constrained to the design-system content width.
3. The heading renders as a single `<h2>` element. The banner never renders an `<h1>`. (Resolves the heading-level question; the page's `<h1>` belongs elsewhere.)
4. The body renders only when the Rich Text field has content. When empty, no empty body wrapper is output in normal (non-editing) mode.
5. The secondary action renders only when its General Link field has a link. When empty, no secondary button or empty wrapper is output in normal mode.
6. Primary action is required for authors: the datasource template marks it as the expected field and sample content always sets it. The component must not crash when it is empty: in normal mode it renders no primary button; in editing mode it renders an editable placeholder (see criterion 12). (Resolves the primary-action question.)
7. Primary and secondary actions are rendered as links (role `link`) with discernible text taken from the authored link text. Both appear in the order primary then secondary.

**Background modes**

8. When a Background Colour option is selected, the banner uses that option's background and text colour pair from the table above.
9. When no colour option is selected, the banner uses the Neutral Light pair (`neutral-100` / `neutral-900`).
10. When a Background Image is set, it is shown instead of the colour background, with a black scrim and white text, regardless of which colour option is selected.
11. Button styling follows the in-scope button rules for each background mode (Neutral Light versus Primary, Neutral Dark, and image).

**Editing**

12. In Pages / Experience Editor mode, every field (heading, body, primary action, secondary action, background colour, background image) is editable, including when empty. Empty optional fields (body, secondary action, background image) render an editable affordance in editing mode only.
13. In editing mode the author can see and select the background image field when it is empty and when it is set.

**Accessibility**

14. Text-to-background contrast meets WCAG AA (4.5:1 for normal text, 3:1 for large text and button boundaries/focus indicators as applicable) for each of the three colour options and for the background-image case. The three colour pairs above are accepted as meeting AA; the image case must meet it for white text over the scrim at the Design-chosen opacity, evaluated against the lightest expected image (white image beneath the scrim).
15. Primary and secondary buttons show a visible focus state when focused by keyboard.
16. At small viewports, the buttons stack vertically; at larger viewports they sit side by side. Verified by unit test where possible and otherwise by manual check at defined breakpoints (Design to define).

**Sitecore configuration (CMS Configuration stage)**

17. The CMS Configuration Record shows these created and verified: datasource template with all six fields and correct field types; background-colour option template; options folder; Neutral Light, Primary, and Neutral Dark option items; rendering with Datasource Template set; availability on the `harness-engineering` site; allowed in `headless-main`; datasource folder under the site's `Data` folder; and sample content.
18. The Background Colour Droplink source resolves site-relatively (`$site` with `#`-escaped segments), and the option items exist before the field that references them.
19. Sample content includes at least one banner with both buttons set on a page and one banner with a background image set. If the image is not uploaded before the CMS stage, the record lists it as a Manual Step.
20. Serialization includes cover every new path (templates, option items, rendering, placeholder settings, content).
21. The layout JSON for the sample page contains the banner rendering in `headless-main` with the expected datasource fields.

**Tests**

22. Unit/component tests cover: all fields populated; secondary action absent; body absent; default colour (no option selected); each colour option; background image mode; and empty fields in editing mode. Tests assert visible behaviour and roles, not CSS classes or internal structure.
23. The existing test suite and lint continue to pass.

## Risks

- Contrast: any colour option without AA-compliant text must be dropped, not shipped. The image case depends on the scrim opacity.
- Overlap with Hero Banner: the CTA banner must stay visually and functionally distinct and uncoupled from it.
- Editing mode: empty optional links and image field must stay selectable in Pages.
- Option items and Droplink source: the source query must resolve site-relatively and the option items must exist first.
- First run of the D-005 CMS stage: `create_component` without `modelId` may not create the `<Name> Folder` template or datasource folder, and `update_component` may not set the rendering's Datasource Template. The agent escalates rather than working around these. The editing host will not run this branch during the CMS stage, so the visual check is likely "not deployed, not verifiable" and the layout JSON (criterion 21) is the main check.
- Primary-action-required is an authoring convention (template help and sample content), not enforced by Sitecore validation, since validation is out of scope.
