## Title

Image Gallery Carousel with Lightbox

---

## Feature Goal

Provide an Image Gallery rendering, placed in the `headless-main` placeholder, that presents a set of authored images as a one-slide-at-a-time carousel (previous/next controls, slide indicators, optional captions). Activating the current slide opens that image full-size in an accessible modal lightbox, where the visitor can step through the gallery and close back to the carousel.

---

## User Value

- Visitors can browse a set of images in a compact region of the page and inspect any image at full size without leaving the page.
- Authors can build a gallery from reusable Gallery Image items (image plus optional caption) with an optional heading, and edit all of it in Sitecore editing mode.
- Keyboard and assistive-technology users get a carousel and modal that meet the accessibility criteria below.

---

## Resolved Task Notes Questions

1. **Heading level: fixed `h2`, not configurable.**
   Reasoning: the Image Gallery data source defines only a single Heading text field, so no level control is authored; a page-level `h1` is expected to be owned by the page or Hero Banner, and a gallery is a section within the page, so `h2` is the correct level. A configurable level adds a template field and author error surface (skipped levels) for no stated need. The h2 assumption is stated here and should be confirmed in Design against the heading structure of existing components; if it conflicts, raise it then rather than adding a field.
2. **Wrap-around: both the carousel and the lightbox wrap (last to next goes to first; first to previous goes to last).**
   Reasoning: indicators allow jumping to any slide anyway, so wrapping adds no new capability, but it avoids disabled controls (which complicate keyboard focus, since a focused control that becomes disabled loses focus) and behaves the same in both surfaces. The current position is always exposed as "Slide x of y" so wrap is not disorienting.
3. **Editing-mode presentation: a non-interactive, fully expanded view.**
   Reasoning: hidden slides and a modal make fields unreachable for inline editing. In editing mode every Gallery Image is rendered as a visible, editable block in authored order (image and caption fields editable), the heading field is always rendered editable (even when empty), and carousel controls, indicators, and the lightbox are not rendered or activatable. An empty gallery in editing mode still renders the editable heading so the component is selectable and the author can see it is empty.

No question requires escalation to a human.

## In Scope

- Image Gallery rendering with an optional heading (fixed `h2`; omitted entirely when empty in normal mode).
- Carousel showing one slide at a time, ordered as authored in the Multilist.
- Previous and next controls; slide indicators showing the current position and usable to jump to a slide; wrap-around at both ends.
- Keyboard operation: all controls reachable and operable by keyboard; Left/Right arrow keys move between slides when focus is within the carousel.
- Optional per-slide caption.
- Responsive layout across design-system breakpoints with a constant slide aspect ratio so the page does not shift when slides change.
- Images rendered from the Sitecore Image field through Next.js Image optimisation.
- Lightbox modal: opens on activating the current slide; shows the image full-size with caption; previous/next across the whole gallery (wrapping); closes via close control, Escape, and backdrop click; dialog semantics, focus moved in on open, focus trapped while open, focus returned to the triggering slide on close, page scroll locked while open.
- Low-count behaviour: one image renders no controls or indicators (lightbox still available); zero images renders nothing in normal mode.
- Editing mode presentation as resolved above.
- Data source template Image Gallery: Heading (Single-Line Text), Images (Multilist referencing Gallery Image items).
- Data source template Gallery Image: Image (Image), Caption (Single-Line Text).
- Registration through the existing `sitecore-tools` component map and as an available rendering for `headless-main`.
- Unit/component tests (see Acceptance Criteria) and a CMS Configuration Guide.

---

## Out of Scope

- Grid or thumbnail-strip layout.
- Autoplay or automatic rotation.
- More than one slide at a time; configurable slides-per-view.
- Swipe/touch-gesture navigation beyond native controls.
- Zoom, pan, pinch-to-zoom in the lightbox.
- Deep-linking to a slide or lightbox image via URL.
- Video or non-image media.
- Download, share, or social actions.
- Selecting media library items directly in the Multilist.
- Per-instance variants, configurable heading level, or transitions beyond a basic slide change.
- Changes to existing components (Hero Banner, Promo Card Grid).
- New npm dependencies (no third-party carousel or lightbox library).
- Mock or fallback content when CMS data is unavailable.
- Dictionary-driven UI labels (B012); labels are hard-coded English strings for now.

## Acceptance Criteria

Source of behaviour: content (heading, images, captions, order) is driven by Sitecore-authored data source items resolved through layout data; placement is driven by placeholder and component-map composition; carousel/lightbox state is application-owned logic.

### Rendering and content

1. AC1: The Image Gallery renders through the existing route and layout pipeline when authored in the `headless-main` placeholder, resolved via the `sitecore-tools` component map, without bypassing placeholder composition.
2. AC2: Slides appear in the order of the Multilist; the first authored image is the initially shown slide.
3. AC3: Exactly one slide is visible at a time in normal mode with two or more images.
4. AC4: When Heading is set it renders as an `h2` (the only heading level used); when empty, no heading element is rendered in normal mode.
5. AC5: When a Gallery Image Caption is set it renders with its slide (and in the lightbox for that image); when empty, no caption element is rendered for that slide.
6. AC6: Each image renders via the Sitecore Image field with Next.js Image optimisation, with `alt` text taken from the image item's alt value. Images not currently displayed are not eagerly loaded at full size (lazy loading or equivalent), and the lightbox image is requested at a size appropriate for full-size display, not at the carousel slide size.
7. AC7: The slide frame has a fixed aspect ratio at every design-system breakpoint; images of differing proportions are fitted within it, so the gallery's height does not change when the visible slide changes.
8. AC8: Layout uses design-system tokens for colour, spacing, typography, and breakpoints, with no hard-coded values where a token exists.

### Carousel navigation

9. AC9: With two or more images, previous and next buttons and one indicator per image are rendered. Each has an accessible name (e.g. "Previous slide", "Next slide", "Go to slide 3").
10. AC10: Activating next shows the following slide; on the last slide it shows the first. Activating previous shows the preceding slide; on the first slide it shows the last.
11. AC11: Activating an indicator shows that slide. The indicator for the current slide is exposed as current (e.g. `aria-current` or equivalent state), distinguishable programmatically and visually.
12. AC12: The carousel is exposed with a labelled carousel region (role/roledescription and an accessible name, using the heading when present), and the current position is available to assistive technology as "Slide x of y". Slide changes initiated by the user are announced via a polite live region or equivalent; no automatic rotation occurs.
13. AC13: All controls are reachable in a logical tab order, operable with Enter/Space, and show a visible focus indicator using the design-system focus style. With focus inside the carousel, Left Arrow moves to the previous slide and Right Arrow to the next (with wrap).
14. AC14: Slides not currently shown are not exposed to assistive technology or the tab order (e.g. hidden from the accessibility tree).
15. AC15: With exactly one image, the slide renders (with caption if authored) and no previous/next controls or indicators are rendered; the lightbox remains available, and its own previous/next controls are not rendered.
16. AC16: With zero images (or an empty/unresolvable Multilist) in normal mode, the component renders no markup, including no heading.

### Lightbox

17. AC17: Activating the current slide (click, or Enter/Space on the focusable slide trigger) opens a lightbox showing that image at full size with its caption if authored. The slide trigger has an accessible name conveying that it opens the image full-size.
18. AC18: The lightbox has dialog semantics (`role="dialog"` with `aria-modal="true"`) and an accessible name (caption, else heading, else a generic label such as "Image gallery").
19. AC19: On open, focus moves into the lightbox (to the close control or dialog container). While open, Tab and Shift+Tab cycle only among the lightbox's focusable elements; content behind it cannot be focused.
20. AC20: With two or more images, the lightbox shows previous/next controls with accessible names and wrap-around, and Left/Right arrow keys step through images. The lightbox's current image is announced as "Image x of y". With one image, no previous/next controls are shown.
21. AC21: The lightbox closes via the visible close control (accessible name "Close"), the Escape key, and a click on the backdrop. A click on the image, caption, or controls does not close it.
22. AC22: On close, focus returns to the slide trigger that opened the lightbox. If the visitor navigated inside the lightbox, the carousel shows the lightbox's last-viewed image on close and focus returns to that slide's trigger.
23. AC23: While the lightbox is open, page scroll is locked; on close the page scroll position and scrollability are restored. Scroll lock is released if the component unmounts while open.

### Editing mode

24. AC24: In Sitecore editing mode, the heading (always rendered, including when empty), every Gallery Image's image, and every caption (including when empty) are rendered as inline-editable fields, in authored order, all visible at once.
25. AC25: In editing mode no carousel controls, indicators, arrow-key handling, or lightbox are rendered or activatable, and no content is hidden from view.
26. AC26: In editing mode with zero images, the editable heading is still rendered so the component remains selectable.
27. AC27: Normal mode and editing mode are selected from the existing Sitecore page-mode context; normal-mode behaviour (AC2-AC23) is unchanged by the presence of the editing path.

### Registration, CMS, and quality

28. AC28: The Image Gallery rendering is registered in the `sitecore-tools` component map and is available in the `headless-main` placeholder; Multilist-referenced Gallery Image fields (Image, Caption) are present in the layout data the component reads.
29. AC29: The CMS Configuration Guide documents both data source templates (field names and types as in In Scope), the rendering definition, `headless-main` placeholder settings / available renderings, creating a data source and Gallery Image items, the Multilist Source configuration (restricting to Gallery Image items), and serialization steps.
30. AC30: No new npm dependencies are added.
31. AC31: Component/unit tests exist and pass for: multiple images; single image; no images; caption present and absent; heading present and absent; carousel navigation by controls, indicators, and keyboard, including wrap-around; lightbox open, navigate (including wrap-around), and close by control, Escape, and backdrop; focus moved in, trapped, and returned on close; scroll lock applied and released; and editing-mode rendering (all slides visible, fields editable, no controls or lightbox). Tests assert visible behaviour, roles, and accessible names, not CSS classes or component internals.
32. AC32: `npm run lint`, `npm test`, and `npm run build` pass from `src/headapps/rob-harness-engineering/`.

## Risks

- Client/server boundary: interactive state needs client components; keep the client surface small (Design to decide the split).
- Accessibility: carousel and modal patterns are common WCAG failure points; AC9-AC23 define the bar and need manual keyboard/screen-reader verification in QA beyond unit tests.
- Heading assumption: fixed `h2` assumes the page's `h1` is owned elsewhere; confirm in Design.
- Performance: images for non-visible slides and the lightbox need a deliberate sizing/lazy-loading approach (AC6).
- Layout shift: differing aspect ratios require the fixed frame and fit defined in AC7.
- Multilist resolution: referenced item fields must be present in layout data (AC28); if they are not, Design or Plan must address how data is obtained without mock data.
- Hard-coded English labels until B012 introduces dictionary-driven labels.
- Wrap-around lets the carousel loop indefinitely with no end signal; mitigated by the "Slide x of y" position exposure.
